# Cloud gateway local process

The root Compose stack provides a separate Cloud gateway on a loopback-bound port. The local Node adapter runs the same request handler shape used by a Cloudflare Worker. The process provides liveness and, when configured, authenticates and authorizes mapped capability requests through the private control plane. Requests that pass authorization still return service unavailable until quota reservation, privacy enforcement, and private worker routing are connected. It does not provide a ready data plane or establish Cloudflare deployment compatibility.

The local adapter reads a classification request body only after authorization and a successful configured readiness probe. Other capability bodies remain unread. It closes responses and bounds header and request timeouts; these settings are local development safeguards and do not replace gateway rate limiting or streaming controls. `/health/live` reports process liveness independently; `/health/ready` returns 503 while the dispatch, privacy, and quota gates are not connected, even if authorization is configured. Readiness must only become successful when those dependencies and their real health are enforced.

Unavailable responses use Problem Details with the 32-character trace identifier in both the response and `X-Trace-Id`. The gateway preserves a valid version-00 [W3C traceparent](https://www.w3.org/TR/trace-context/) trace ID or generates a new one when it is absent, duplicated or malformed, and generates a new parent ID. It forwards that context to the private authorization, classification readiness and privacy calls without attaching request content. `tracestate`, later trace-context versions and the remaining execution stages are not propagated yet.

The admission component orders authentication, authorization, request preparation, deployment resolution, and quota reservation. Request preparation may inspect the body only after authorization. Only an explicit newly reserved quota result permits admission; duplicate, malformed, failed, or cancelled requests never permit dispatch. Cancellation after reservation leaves the hold for reconciliation. It accepts trusted adapters and fails closed on adapter errors. It is not wired to the local handler; production adapters, settlement, request validation, and dispatch are still required before execution can be enabled.

The private classification reservation endpoint and Node client provide an authenticated quota-admission building block. The control plane revalidates the classification credential over pinned mutual TLS and derives tenant and application from it; the caller supplies a request ID, keyed fingerprint, key ID and stable expiry no more than five minutes away. The unit and amount are fixed to one classification `request`. A replay with the same fingerprint, key ID and expiry returns `duplicate` and must not start a second execution; changed inputs return an idempotency conflict. A hold remains reserved after ambiguous failures. This endpoint is not called by the public gateway yet: deployment-managed fingerprint keys, execution fencing, worker dispatch and settlement must be connected before admission can safely enable execution. The local mutual-TLS test uses a disposable PostgreSQL database and does not prove Cloudflare deployment or production key custody.

For a retry, the scoped private fingerprint lookup returns both the retained key ID and the original reservation expiry. The Node client preserves the expiry string without converting it through JavaScript's millisecond timestamp precision; the reservation service compares the stored microsecond value. Expired, legacy or unavailable retry metadata does not authorize another execution.

The fingerprint configuration helper accepts an active key ID and an absolute path to a deployment-managed secret file with one `key-id:base64` entry per line. It validates canonical base64, key lengths, duplicate IDs and the active ID, and clears the input and temporary key buffers after constructing the retained in-memory keyring. This helper is not yet invoked by the local gateway startup; mounting, key retention, rotation operations and runtime wiring remain necessary.


The optional control-plane authorization endpoint is enabled with `OpenConnect:Cloud:GatewayTrust:Enabled` and one to sixteen SHA-256 leaf-certificate fingerprints under `OpenConnect:Cloud:GatewayTrust:ClientCertificateSha256`. It requires direct HTTPS, a client certificate with client-auth usage, a current validity period, and an exact configured fingerprint; forwarded certificate headers are not identity. Kestrel must be configured with a server certificate and an HTTPS listener. Pin updates require deployment configuration refresh; overlapping pins support certificate rotation. Only the gateway client certificate is accepted by the opt-in HTTPS client-certificate callback. The endpoint bounds its request and returns only credential-derived application identity and authorization status, never the credential. Public docs remain independent when the feature is disabled.

A Node HTTPS client validates the server certificate and hostname, supplies the configured client certificate, bounds response size and deadline, and rejects redirects or malformed responses. An integration test exercised this client over real mutual TLS to Kestrel and PostgreSQL, including untrusted clients, untrusted server identity, and revoked credentials. The local gateway uses this client when configured but does not dispatch authorized requests. Configure `CLOUD_AUTHORITY_ORIGIN`, `CLOUD_AUTHORITY_CA_FILE`, `CLOUD_AUTHORITY_CERT_FILE`, and `CLOUD_AUTHORITY_KEY_FILE` together, with absolute paths to read-only certificate and key files mounted by the deployment. Partial configuration fails startup; no configuration retains fail-closed behavior. The root Compose service forwards these settings but does not mount credentials by default. A local HTTP gateway to mutual-TLS control plane and PostgreSQL test verifies authorization and revocation. Private network deployment, live certificate provisioning, quotas, request validation, and active-call revocation remain outstanding.

The classification readiness probe checks the existing worker's `/health/ready` and bearer-protected `/internal/v1/capabilities` over deployment-owned mutual TLS. It requires a real engine, an exact configured model revision and a classification advertisement that does not grant tools. It bounds responses and timeouts and does not return worker diagnostics. Configure `CLOUD_CLASSIFICATION_ORIGIN`, `CLOUD_CLASSIFICATION_CA_FILE`, `CLOUD_CLASSIFICATION_CERT_FILE`, `CLOUD_CLASSIFICATION_KEY_FILE`, `CLOUD_CLASSIFICATION_TOKEN_FILE`, `CLOUD_CLASSIFICATION_MODEL_REVISION`, `CLOUD_CLASSIFICATION_ENDPOINT_REFERENCE`, `CLOUD_CLASSIFICATION_REGION`, and `CLOUD_CLASSIFICATION_CONTRACT_VERSION` together. Existing configured probes must add the last three values; partial configuration fails startup. File paths must be absolute and provided through deployment-managed mounts. Compose forwards these settings but does not mount credentials.

After successful classification authorization, the gateway asks the pinned mutual-TLS control plane to revalidate the machine credential and match the deployment-owned reference, region, contract and model revision against an enabled inventory entry before probing. A missing, disabled or mismatched entry stops the call before worker contact and body inspection. The configured origin-to-reference mapping is deployment-controlled and is not independently attested; inventory changes can race a probe. This exact inventory match does not verify tenant residency policy, readiness, signatures, artifact integrity, capacity, active-call revocation or authorization to dispatch. A local gateway-to-PostgreSQL test verifies matching and disabled cases with simulated worker readiness. A separate local mutual-TLS proxy test exercised the actual classification worker in fake mode and verified rejection; positive real-engine tests used simulated responses. Valid requests still return 503 because quota, residency and dispatch are not connected.

Classification requests use the versioned Cloud JSON Schema and OpenAPI contract. The local gateway enforces a 65,536-byte UTF-8 JSON body limit, rejects duplicate properties and unknown fields, and checks the worker-derived input and configuration bounds. Inline text or an opaque input reference may be supplied, but references are not resolved and neither form is dispatched. The current envelope does not yet define TTL, idempotency, streaming or execution deadlines; these remain prerequisites for execution. Shared fixtures are checked by both the gateway tests and the repository JSON Schema validator.

For inline classification text, the gateway calls the control plane's private `/cloud/internal/v1/classification/privacy` endpoint after authorization, readiness and request validation. The endpoint requires direct pinned mutual TLS and revalidates the machine credential and classification entitlement before reading the bounded UTF-8 body. It applies the existing .NET rules detector with Cloud-derived tenant, application and request scope; detected sensitive content is blocked rather than tokenized until durable scoped redaction is available. Before returning a decision, the endpoint writes a Cloud-side metadata observation containing scope IDs, request ID, trace ID, outcome and timestamp; it contains no content or detected values. PostgreSQL rejects update, delete and truncate, and storage failure fails closed. Observations describe evaluations, not worker execution or application-host inspection; repeated request IDs produce separate observations. They are not signed or deduplicated receipts, and retention, integrity verification, and host receipts remain outstanding. Missing or failed detectors fail closed, and opaque input references remain unavailable. A local gateway, mutual-TLS control plane and PostgreSQL test verifies clean, blocked, revoked, untrusted-client, evidence failure, trace correlation and append-only paths; the worker readiness result in that test is simulated. Gateway execution remains disabled.
