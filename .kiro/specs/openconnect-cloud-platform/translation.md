# Translation capability status

Cloud translation remains unavailable until the gateway has authenticated admission, scoped privacy inspection, quota, fenced execution, settlement and output checks, and a provisioned real decoder has been verified. The existing deterministic fake engine is for explicit non-production testing and must not be presented as translation service readiness.

The versioned Cloud translation input contract accepts bounded inline text and source and target language identifiers. Its gateway parser rejects duplicate fields, malformed Unicode, unknown properties, unsupported media and expired deadlines, and clears the original request buffer after processing. The parser is not a routed endpoint: a syntactically valid pair must still be checked against an eligible deployment before reservation, and the complete execution and privacy path remains required.

The gateway worker contract produces the exact NLLB payload for claim binding and validates untrusted output against the requested language pair and pinned model revision and tokenizer hash. The private dispatcher uses bounded mutual-TLS transport, rejects a payload that differs from the request bound to the claim, and does not retry ambiguous requests. Preparation and dispatch do not authorize or inspect the input, and validated output still requires privacy screening. The dispatcher is not yet connected to a public endpoint or authoritative deployment selection.

A Cloud-side translation privacy service separately screens all worker-visible input fields and translated output with the configured detector, rejects malformed Unicode and fails closed when a decision is unavailable. An append-only input evidence store binds decisions to tenant, application, request fingerprint and character count; its admission query uses the latest decision and requires callers to hold the application lock. The private input inspection endpoint requires a trusted gateway certificate and an authorized translation credential, and fails closed if evidence cannot be recorded. Quota admission, execution and output release are not yet connected; these components do not make translation available. The evidence migration intentionally retains records on rollback.

Translation character reservations have a dedicated transactional store: it locks the application, requires the latest matching input decision, rechecks expiration, and atomically reserves capacity. Private gateway endpoints expose reservation and fingerprint-key lookup after translation-scoped authorization. A bounded mutual-TLS gateway client validates privacy and quota responses; it is not yet connected to gateway admission or execution claims. A reservation does not authorize worker execution or result release.

The worker-side claimed execution boundary validates a canonical bounded payload and configured text limit, checks the supported language pair, consumes the exact payload before invoking the engine, accepts only real-engine output matching the expected model revision and tokenizer hash, and releases the result only after settlement. Ambiguous consumption or settlement fails closed. A private client uses bounded mutual-TLS requests, derives a keyed payload fingerprint and never retries an ambiguous mutation. The opt-in private worker route rejects fake engines, blocks the legacy execute route in Cloud mode and requires a translation-specific control-plane readiness response matching its deployment identity. Its inbound worker connection requires deployment-provided mutual TLS or a private mutually authenticated proxy; the default standalone HTTP listener is not sufficient for Cloud deployment. The translation readiness, claim and settlement control-plane endpoints are not yet implemented, so the private route remains unavailable. The outbound client transport is tested against an isolated TLS fixture; Cloud privacy screening and public translation are not yet connected. Python may retain immutable copies of request content and key material.

For flat local NLLB bundles, the manifest helper checks the weights SHA-256 and tokenizer SHA-256 against the manifest as well as the license policy; flat bundles are not eligible for decoder execution. The worker does not advertise real translation or report real readiness unless the selected versioned bundle, license, runtime load and local smoke check succeed. A verified bundle alone does not establish that the model is safe, commercially licensed, or operational.

The decoder bundle resolver requires an explicitly active, fingerprint-matched versioned revision and verifies its complete declared assets, license policy and on-disk contents without fetching. Its initial supported layout is a single `model.safetensors` with declared model configuration, tokenizer and tokenizer configuration; undeclared, duplicate, linked or incomplete files are rejected. The offline CPU decoder uses local-only model loading, a pinned optional runtime, explicit language tokens, bounded generation and serialized tokenizer access. Readiness and execution require an explicitly selected model and a successful smoke check. A synthetic random M2M100 model verifies local loading, generation and the worker HTTP path only; it does not establish translation quality. Real model and Cloud route acceptance remain outstanding. Mounting the verified cache read-only and controlling concurrent asset replacement remain deployment responsibilities.
