# OpenConnect Cloud Platform Design Decisions

## Code organization

Cloud code is grouped by feature (`Tenants`, `Capabilities`, and `Credentials`), with HTTP routing in `Http` and database infrastructure in `Persistence`. HTTP handlers delegate database operations to services. Tenant operations use a persistence port; membership checks and writes remain together in the persistence implementation. Capability reads load tenant-scoped snapshots through a persistence port and project entitlement and dependency policy in the capability feature. Capability selection policy runs in the capability feature through a transaction-aware persistence port; its adapter loads authorization and selection facts, commits selection and audit together, and maps serialization conflicts without claiming an unobserved revision. Credential secret generation, parsing, environment tags, and fixed-time comparison are isolated in the credential feature. Credential operations use a transaction-aware persistence session; EF Core owns context lifetime, serializable transactions and persistence queries. Credential issuance and rotation continue to load capability data using the same EF context and serializable transaction as the credential write.

Status: Decisions for the current portal identity foundation; broader platform design remains governed by [`docs/plans/openconnect-cloud-requirements-spec.md`](../../../docs/plans/openconnect-cloud-requirements-spec.md).

## OC-CLOUD-ADR-001: Extend the existing Blazor portal

**Decision:** Keep the current ASP.NET Core / .NET 10 Blazor application as the public documentation host and add a separate Cloud layout and protected routes.

**Rationale:** The existing site is static-rendered by default and already hosts documentation and API reference. Cloud services must not make those public routes depend on new infrastructure.

**Status:** Implemented in the portal route/layout layer. Tenant/application and initial catalog persistence are implemented; entitlement administration and data-plane services remain pending.

## OC-CLOUD-ADR-002: External OIDC with server-side session cookie

**Decision:** Cloud identity is opt-in configuration. When enabled, use external OIDC authorization code flow with PKCE and a `__Host-` HttpOnly, Secure, SameSite=Lax session cookie. Do not add local password authentication. Sign-out is an authenticated, antiforgery-protected POST. Generic OIDC sign-out also ends the provider session; Google sign-out ends the Cloud session only.

**Rationale:** The Cloud portal must not invent password handling, expose provider credentials to browser assets, or weaken public documentation availability.

**Configuration:** `OpenConnect:Cloud:Identity:Enabled`, `Authority`, `ClientId`, and `ClientSecret`. Supply the client secret through the deployment's secret store. Enabling identity with any required value absent fails startup. Google sign-in can be independently enabled with `OpenConnect:Cloud:Identity:Google:Enabled`, `Google:ClientId`, and `Google:ClientSecret`. Register `/cloud/signin-google` as an exact authorized redirect URI on the public HTTPS origin. The Google issuer is `https://accounts.google.com`; validated subjects remain separated by issuer. Existing OIDC cookies without a locally stamped issuer remain valid only when the original subject claim issuer matches the enabled configured authority; other legacy sessions must sign in again. The session cookie is rejected when its provider is disabled or its stamped issuer no longer matches an enabled provider. With both providers disabled, Cloud sign-in returns service unavailable and no Cloud identity is asserted. Google client credentials belong in the deployment secret store. Local in-process HTTP tests exercise provider selection, disabled-provider behavior, authorization redirects and PKCE with synthetic discovery metadata. Focused tests also cover issuer claim replacement and provider-scoped invitations. An authenticated Google callback, browser sign-out, and deployment remain unverified.

**Status:** Implemented; external provider interoperability and production cookie behavior still require deployment-specific verification.

## OC-CLOUD-ADR-003: No synthetic tenant or security state

**Decision:** The dashboard reads organization and service state from the Cloud control-plane store. It must not manufacture data, treat selection as execution authorization, or translate detector output into enforcement claims. Usage and evidence remain explicitly unavailable until connected to authoritative sources.

**Rationale:** A Cloud security or entitlement dashboard is an evidence surface; missing authoritative records must remain visibly missing.

**Status:** Implemented for the organization/application/catalog dashboard. Plan entitlement administration, receipt ingestion, usage, and security evidence remain pending.

## OC-CLOUD-ADR-004: Separate PostgreSQL Cloud control-plane schema

**Decision:** Keep Cloud entities in a dedicated `cloud` schema and DbContext in the portal host, isolated from public documentation readiness and existing application persistence. Configure it only through `ConnectionStrings:CloudControlPlane`. Do not apply migrations automatically at portal startup; manage them explicitly with the repository-pinned EF tool.

**Rationale:** The public portal must remain available when Cloud PostgreSQL is absent or unavailable, and Cloud migrations must not alter existing application tables.

**Status:** Initial PostgreSQL migration and model snapshot are implemented. A live database migration and restore test have not been run.

## OC-CLOUD-ADR-005: Tenant-scoped identity and initial roles

**Decision:** Bind each membership to its validated identity provider issuer and `sub` claim. Organization creation atomically makes the creating identity an `Owner`. Only `Owner` and `Administrator` may create applications. Tenant reads always filter by both tenant ID and the authenticated identity's membership; unknown and non-member tenant access returns the same not-found response.

**Rationale:** Tenant IDs are identifiers, not credentials. Every resource read must independently establish membership, and app registration changes are privileged within a tenant.

**Status:** Implemented for organization/application creation and reads. Invitations, role changes, removal, recovery, broader role actions, and provider-to-provider subject migration remain pending.

Application creation reads the actor's membership and writes the application and audit event in the same serializable transaction. Concurrent membership administration must use a compatible transactional protocol and handle serialization failures without granting access.

## OC-CLOUD-ADR-006: Separate capability definitions, entitlements, and selections

**Decision:** Store logical capability definitions separately from worker deployment state, tenant plan grants, tenant selections, and application selections. An entitlement or enabled selection alone never means that a backend is ready. The initial catalog marks platform availability `not_configured` and marks modality/region metadata unverified until source contracts and deployment policy establish them.

**Authorization rule:** Organization enablement requires a current plan grant, platform availability, and all recursively declared dependencies to be entitled and selected. Application enablement additionally requires the organization selection. The future Cloud gateway must still validate credential scope, policy, region, deployment readiness, and quota before any execution.

Application dependencies must also be selected for that application. Read views and selection writes evaluate the recursive dependency chain at both organization and application scope.

Capability eligibility and dependency evaluation are isolated in a policy component. Persistence remains responsible for obtaining the relevant state inside the applicable transaction; the policy does not issue database queries.

**Concurrency:** Service-selection API writes require a quoted numeric `If-Match` revision. Updates use EF concurrency tokens and a PostgreSQL serializable transaction. Successful changes and audit events commit together. Stale updates and PostgreSQL serialization conflicts return conflict; disabling remains possible after availability or entitlement loss. Wrapped PostgreSQL conflicts do not return a guessed current revision; clients reload.

**Status:** Catalog/selection persistence, authenticated read APIs, revisioned write APIs, and portal views are implemented. Plan grants, platform deployment health updates, gateway admission, quota, and PostgreSQL concurrency execution remain pending.

## OC-CLOUD-ADR-007: One-time scoped machine credentials

**Decision:** Issue credentials only to tenant owners/administrators for an application and a non-empty list of currently selectable service scopes. Generate a 256-bit random secret, return it once with `Cache-Control: no-store`, and persist only SHA-256 of the full key plus a short fingerprint. Credential metadata binds tenant, application, environment, scopes, issue/expiry/revocation/last-use. Rotation atomically revokes the previous credential and creates its replacement. Revocation takes effect in the control-plane store before the API returns.

Issuance and rotation require an explicit future expiry; permanent credentials are rejected. Authentication rejects existing credentials without an expiry; issue replacements with an expiry.

Revocation and rotation read and modify credential state in serializable transactions. A concurrent update must not silently overwrite a revocation; serialization failures require callers to reload and retry the operation.

Credential authentication rechecks revocation, expiry, and application environment in the database when recording last use. Revocation after this check still requires gateway admission and active-session cancellation; authentication alone is not execution authorization.

**Authentication format:** `oc_<environment>_<credential-guid>_<base64url-random-secret>`. Validation performs fixed-time hash comparison and checks revocation, expiration, and application environment. The resulting credential identity and scopes are inputs to later gateway admission; successful credential authentication alone does not authorize a capability call.

The parser splits only the first three separators because the base64url secret may itself contain underscores.

**Exposure boundary:** Credential material is returned once by the authenticated management API or displayed once in the authenticated interactive portal at issuance/rotation. It is never placed in static assets or logged by the control plane. The operator must transfer it to server-side secret storage; the portal clears its displayed value when dismissed or when navigating to another application.

The portal associates asynchronous reads and writes with the selected application generation. Results from a prior selection are discarded when navigation or disposal occurs; a credential issued during navigation may need revocation if its one-time value was not displayed.

Credential rows distinguish expired and revoked credentials and label repeated management actions with their fingerprint. Cloud controls use explicit light and dark focus and button styling. A local OIDC browser check covered keyboard focus and credential creation, dismissal, and revocation in light mode at 390px and dark mode at 1280px; broader assistive-technology and deployment verification remains required.

Machine admission now validates a server credential, derives its credential, tenant and application identity and checks its scope before reading current entitlements and selections. A repeatable-read database snapshot rechecks credential expiry, revocation and application binding and evaluates the capability dependency policy. This is a control-plane component only: it does not sign snapshots, implement residency or deployment policy, reserve quota, cancel active streams or authorize gateway dispatch. Credential and selection changes occurring after its snapshot need a separately defined active-call revocation policy.

**Status:** Hash-only persistence, one-time API response, list, rotate, revoke, and credential validation logic are implemented. Gateway integration, credential rate limits/abuse controls, real database revocation-latency proof, and client onboarding UX remain pending.

Issuance and rotation evaluate capability scopes in the same serializable database transaction as the credential write. The credential persistence session loads the capability snapshot through the same EF context and serializable transaction as the credential write, without exposing EF Core to the credential service. A disposable PostgreSQL test verifies tenant and application read isolation and selection projection, alongside the credential issuance and revocation concurrency tests.

## Deferred decisions

The root Compose stack includes a separate `cloud-gateway` process with a local Node adapter around a Worker-compatible request handler. Its liveness endpoint responds while all other requests fail closed with 503 until identity, admission, quota, and worker routing are implemented. This local process does not establish Cloudflare deployment or production readiness.

Plan-grant administration, policy cache/revocation, gateway runtime, worker authentication, receipt signature format, quota authority, retention, and billing are intentionally not decided by this portal/control-plane foundation. Resolve each against the main requirements and source contracts before its implementation; do not infer production behavior from a UI placeholder.

## OC-CLOUD-ADR-008: Initial atomic quota reservations

Each tenant can maintain an explicit allowed-region list through a versioned region-policy API and the organization regions page. Only tenant owners and administrators can change it; tenant members can read it. A missing policy and an empty list both deny all regions. The page offers verified catalog regions as selectable options and retains previously selected regions that are no longer declared. Successful changes and rejected write attempts are audited without recording request bodies. A separate operator-only API and portal page maintain each capability's region list and verified flag using a revision protected against concurrent updates and older catalog writers; the flag records an operator declaration, not independently established geographic fact. Classification deployment matching requires an enabled matching deployment whose region is present in both the tenant policy and the capability catalog's verified region list. Unverified, missing or mismatched region metadata denies the match before a worker probe. The claim transaction locks and rechecks the tenant policy, catalog and selected deployment, then records deployment ID and region with the claim. A policy or deployment change committed first prevents the claim; a later change does not cancel an already committed claim. The new policy table is not backfilled: deployments must provide explicit tenant policy and verified catalog metadata before matching can succeed. Existing claims have no deployment binding and remain unavailable for automatic classification settlement. This is an inventory and policy check, not independent geographic attestation. Real-browser accessibility and responsive verification, active-call cancellation and production deployment validation remain required. Roll back application code without dropping tenant policies, catalog revisions or claim evidence.

The catalog revision migration locks the capability table while installing a trigger and backfilling existing revisions. It does not change existing region declarations or verify any locations. Operators must assess lock duration for production data, apply the migration before starting the region administration API, and preserve its revision table and trigger during application rollback.

For a claimed classification request, a separate completion service accepts a trusted caller's `completed` observation bound to the tenant, application, reservation and claim ID. It atomically appends an immutable completion observation, finalizes one `request`, moves one reserved unit to consumed, and lets the existing database trigger append usage. Repeated matching completions are idempotent. A private pinned mutual-TLS endpoint and Node client expose this operation to the gateway, requiring a currently valid classification-scoped credential and deriving its tenant and application. The endpoint does not recheck current entitlements or selections because work was already claimed; a credential revoked or expired before completion leaves the hold for recovery. The trusted gateway must only report a completed worker response: the observation is not independently verified or signed. The database guard allows claimed finalization only with a matching completion and a full reservation charge; ordinary and older finalizers cannot release a claimed hold. A worker failure or ambiguous outcome remains held because the current worker contract does not establish whether execution occurred or how to reconcile it. The opt-in public classification handler calls this endpoint after a validated worker response; real worker termination is not yet verified. Apply the completion migration before using the service; roll back application code without dropping completion evidence.

Execution admission has a durable, append-only, tenant/application-scoped single-use claim per fingerprinted reservation. The store locks the reservation before checking capability, expiry, prior finalization and prior claim; competing claims cannot both succeed. A claim must match the stored key ID and request fingerprint. Current quota finalization takes the same lock and refuses to settle a claimed reservation, so a racing refund cannot release capacity after an execution claim. A database trigger also rejects legacy transactional finalizers after a claim, including a writer that began waiting before the claim committed. The guard migration locks the reservation and claim tables and aborts if any existing claim has already been finalized; production lock duration and reconciliation for such an inconsistency are not yet established. Direct database writes to bucket balances outside the finalization transaction are not protected by this guard. Claims are not leased or automatically retried: a crash after claim leaves capacity held for reconciliation. A private pinned mutual-TLS endpoint lets a gateway request a classification claim after revalidating its machine credential; the credential supplies tenant and application. The claim transaction locks and rechecks the credential, application environment, catalog, tenant entitlements, and tenant/application selections, including dependency policy, through commit. A revocation or disable acknowledged first prevents a later claim; a claim committed first is not cancelled by subsequent changes. These conservative locks cover the full catalog and the tenant's selection rows, so contention and production scalability require measurement. Claim identifiers alone are not worker authorization tokens. The Cloud worker route checks a payload-bound, single-use consumption through its own mutual-TLS identity. Opt-in classification routing uses claim-aware settlement; proof of termination, recovery and production deployment validation remain required. Apply both claim migrations before enabling claims or deploying code that finalizes quota; do not drop the append-only claim table or guard when rolling back application code.

Validated classification requests may be processed through a bounded callback that receives the original body bytes and clears the supplied buffer after processing, including on errors. The caller must authorize before invoking it and must not retain copies of sensitive bytes. A classification quota adapter combines these bytes with the authorized identity and retained HMAC key, then calls the private reservation service. It preserves the original reservation expiry for retries and fails closed when the retained key is unavailable. This adapter requires a validated v2 deadline and is wired into the opt-in public handler after privacy admission; recovery and production release gates remain outstanding. Node tests exercise the adapter with simulated responses; a disposable PostgreSQL and mutual-TLS integration test verifies reservation, retry across key rotation, changed-body conflict and the persisted fingerprint against the .NET implementation. The classification worker logs a fixed message on unexpected model failures because exception messages and caller-provided task IDs can contain sensitive request data.

The execution-consumption store records at most one start authorization per reservation. It locks the deployment and reservation, verifies an enabled classification deployment and the claim's deployment and region, and rejects expired or finalized reservations. An append-only table and database trigger bind the consumption to the claim; concurrent callers receive one success and subsequent denials. A consumption is not proof of worker execution or completion. An optional private endpoint accepts a worker client certificate pinned to a configured deployment ID; the endpoint derives that ID from the certificate rather than request data. Configure `OpenConnect:Cloud:WorkerTrust:Enabled` and `OpenConnect:Cloud:WorkerTrust:Certificates` entries with `DeploymentId` and `ClientCertificateSha256`; duplicate pins and overlap with gateway certificate pins fail startup. Multiple distinct pins can identify one deployment for rotation. The HTTPS listener accepts configured gateway and worker pins, while each endpoint enforces its own role. Apply the additive migration first; application rollback must preserve consumption records. Mutual-TLS and PostgreSQL tests cover role separation, concurrent attempts, incorrect identifiers, a disabled deployment and append-only enforcement. A bounded Python worker client verifies the server certificate, presents its deployment certificate, rejects redirects and ambiguous responses, and never retries a consume automatically. An opt-in integration test exercises the Python client against the endpoint and PostgreSQL. The opt-in Cloud worker route invokes it before engine execution; termination, recovery, production rollout and independent security review remain necessary. Existing unbound claims cannot be consumed.

Classification claims can carry a 32-byte HMAC-SHA-256 fingerprint of the exact worker payload. The gateway binding helper generates a fresh 256-bit key for each payload; the claim persists only the keyed fingerprint. The worker client recomputes the fingerprint over the supplied payload bytes and sends it over mutual TLS, and consumption compares it in constant time before recording the start authorization. Claims without a payload fingerprint fail closed at consumption, including previously created claims. The key and payload must be transferred privately and cleared by their owner; a worker must execute exactly the bytes it verified. The Cloud worker route validates the payload, consumes its matching claim, and executes the parsed payload only after success. The opt-in gateway dispatches through this route, while the existing completion endpoint can still record an independently trusted gateway observation without a consumption. This implementation is not production-ready until its remaining release gates are met. Apply the additive claim-column migration before upgrading services, retain old claim and consumption records on rollback, and reconcile stranded legacy claims rather than backfilling unverified proofs. Node, Python and PostgreSQL mutual-TLS tests exercise the binding and Cloud worker route using the fake test engine; real-model execution, independent cryptographic review and deployment key handling remain outstanding.

Cloud worker execution is opt-in through `OPENCONNECT_CLOUD_CONSUMPTION_ENABLED=true`, `OPENCONNECT_CLOUD_AUTHORITY_ORIGIN`, `OPENCONNECT_CLOUD_AUTHORITY_CA_FILE`, `OPENCONNECT_CLOUD_WORKER_CERT_FILE`, and `OPENCONNECT_CLOUD_WORKER_KEY_FILE`. The certificate and key paths must be absolute and deployment-controlled. A Cloud-configured worker rejects the legacy execute route to prevent bypass; without Cloud configuration the legacy route retains its existing behavior. The Cloud route requires the worker bearer credential, validates and bounds the envelope and payload, rejects duplicate JSON fields, and consumes a claim before running the engine. A private gateway adapter prepares the worker payload once and sends those exact bytes with the claim and per-request key over mutual TLS, accepting only bounded, pinned real-model responses. A private sequence composes reservation, payload-bound claim, dispatch and successful settlement, returning a result only after settlement; duplicate and ambiguous requests never dispatch again. The public handler invokes the sequence only after authorization, deployment matching and privacy admission when execution is explicitly enabled. Tests cover the control-plane and PostgreSQL sequence with a simulated worker, not real inference. A crash after consumption leaves quota held for reconciliation. Python and JavaScript cannot guarantee clearing immutable decoded copies of input and key material, and cancellation of the HTTP request does not prove that an already-started model call has stopped.

Gateway classification execution is disabled by default. `CLOUD_CLASSIFICATION_EXECUTION_ENABLED=true` requires the private control-plane and worker-probe configuration, `CLOUD_CLASSIFICATION_DEPLOYMENT_ID`, plus `CLOUD_FINGERPRINT_ACTIVE_KEY_ID` and the absolute `CLOUD_FINGERPRINT_KEYS_FILE` secret path. Incomplete configuration fails startup. Only v2 requests can execute; successful responses use `openconnect.cloud.classification.result/v1` and are returned after settlement. `/health/ready` reports classification readiness only when execution is configured, the gateway's pinned certificate reaches a migrated control plane, and the pinned real-model worker can reach that control plane with a certificate for the configured, enabled deployment ID. The classification worker can load an operator-supplied CPU ONNX bundle only when the deployment pins the contract digest, the asset digests and label mapping validate, the license is accepted, and a smoke inference succeeds. It advertises only that bundle label-set version; the gateway rejects other versions before privacy inspection and quota reservation. The repository supplies no production model, and the synthetic model used in tests does not establish model quality or production acceptance. This check does not establish tenant entitlements or available quota and does not make other capabilities ready. Optional unclaimed-reservation recovery is enabled separately with `OpenConnect:Cloud:QuotaRecovery:Enabled`; it scans every 30 seconds in batches of at most 100. While classification is in flight, the gateway revalidates the same credential, entitlement scope, deployment and region policy before dispatch, approximately every second during the worker call, before settlement and before returning a result. A denied or unavailable check aborts the gateway's worker request and fails closed. Each check has a two-second timeout; timing is not a measured revocation SLA. Cancellation of the HTTP request does not guarantee that the worker's model thread has stopped, so uncertain work and capacity remain held. It is an opt-in integration path, not a production release: emergency termination and claimed-orphan reconciliation are not implemented, and real-model, staging and independent security acceptance are outstanding. Do not expose this path as production-ready until those gates pass.

Each classification deployment's concurrency limit is enforced across gateway instances at claim time. The control plane locks the deployment and counts its unfinalized claims; a database trigger applies the same guard to older claim writers. The trigger updates the deployment row without changing its configured limit so repeatable-read writers with stale snapshots fail serialization instead of exceeding capacity. A slot is retained until the reservation is finalized, even after its deadline or a gateway crash; this deliberately sacrifices availability until safe reconciliation exists. Lowering the limit does not cancel existing claims. Existing over-limit holds are retained and prevent new claims until capacity falls. Mixed-version writers can encounter deadlocks and must fail closed; row churn, lock contention and migration lock duration require production measurement. Apply the additive guard migration before rolling out application changes and retain the guard when rolling back application code. Disposable PostgreSQL tests cover current and older concurrent writers, a stale repeatable-read snapshot and release after completion; production load and recovery are not verified.

Quota buckets carry a database-managed limit revision for future conditional policy updates. Existing buckets start at revision 1, and a PostgreSQL trigger increments it when any writer changes the limit; reservation and consumption counter changes do not increment it. This prevents a stale revision from silently replacing a limit after an older writer updates it. The revision does not itself provide quota administration, tenant entitlement enforcement, or overlap prevention. Policy writers must also preserve the database's balance constraint and use atomic concurrency checks.

Platform operators can provision or revise an application quota bucket through a scoped operator API. The write requires a current operator identity, antiforgery token and quoted `If-Match` revision; revision zero creates a bucket. The application must belong to the named tenant and the capability must exist in the catalog. Catalog billing descriptions are display text, not machine-readable unit lists: classification supports the explicit `request` quota unit; separately measured model compute and compound descriptions for other capabilities need defined units before they can be provisioned. Single-token catalog units are accepted as specified. Scope and period cannot be changed after creation. Serializable transactions reject overlapping periods among policy API writers, and conditional limit updates preserve concurrent reservations and consumption. Successful changes and rejected attempts are audited. The API returns the resulting bucket and revision. Direct or older database writers do not participate in the overlap check; admission continues to fail closed when active buckets overlap. There is no operator UI or tenant administrator quota editing, and this does not establish purchased-entitlement ceilings or gateway admission.

The gateway includes a bounded in-memory HMAC keyring that reproduces the control plane's length-prefixed request fingerprint. A new request selects the active key; a retry must use the stored key ID, and a missing retained key or unverifiable legacy reservation fails closed. The private classification key-ID lookup requires pinned mutual TLS and a current classification credential; it derives tenant and application from that credential and filters by capability. It returns key IDs, never key material or request content. PostgreSQL and Node tests cover app/capability isolation, key lookup, legacy records and a shared .NET/Node fingerprint vector. The gateway uses the keyring for opt-in classification reservation and dispatch. Deployment-managed key distribution and retention, production fencing validation and reconciliation remain required.

Application and capability quota buckets use integer units, a bounded period, an explicit hard limit, and separate reserved and consumed totals. No default allowance is inferred when a bucket is missing or periods overlap. A conditional PostgreSQL update reserves capacity atomically; a tenant/application-scoped request ID and 32-byte request fingerprint bind retries, and repeated requests return a duplicate status that does not authorize a second execution. A mismatched fingerprint or key version is a conflict. The canonical HMAC-SHA-256 input uses length-prefixed version, key ID, tenant, application, capability, HTTP method, route, media type, and authorized request bytes. The key is supplied by trusted server-side infrastructure and must be at least 256 bits. Reservations retain the key version for scoped retry lookup; unknown or missing historic key versions must fail closed. Reservations written before fingerprint or key-version support remain held and their retries fail closed as conflicts; finalization remains available. The database binds each reservation to the same tenant and application as its bucket. Finalization moves an amount no greater than the reservation from held to consumed in one transaction and is idempotent. A measured overage remains held for reconciliation rather than being silently discarded.

An optional quota recovery worker releases only expired, unclaimed classification request reservations after a five-minute grace period. It uses bounded batches and PostgreSQL row locks with skip-locked coordination; finalization and bucket adjustment commit together. A database trigger locks the reservation and prevents older writers from inserting a claim after finalization. Claimed reservations, other capabilities and recently expired reservations remain held. The recovery worker is disabled by default and requires all control-plane migrations. Before enabling it, deploy and verify that every classification execution path requires a durable claim; the database cannot fence an older worker that bypasses claims. Claimed or ambiguous executions still require proof of termination and reconciliation. The opt-in classification path uses these primitives with gateway-side fingerprinting, claim enforcement and usage records. Production secret distribution and retention, billing, claimed-reservation cleanup, full policy administration and reconciliation remain outstanding. Before gateway use, an authenticated caller must compute the keyed HMAC using a retained server-side key; storing a plain content hash could disclose low-entropy payloads. Deployment key rotation and mixed-version execution policy remain unresolved. Period/expiry evaluation currently requires synchronized control-plane clocks. A disposable PostgreSQL test covers migration of existing control-plane data, 100 concurrent reservations near the limit, repeated requests and finalization, tenant binding, and retained expired holds.

## OC-CLOUD-ADR-009: Usage capture during quota finalization

A database trigger atomically captures usage on quota finalization, including writes from earlier application versions. Existing finalized reservations are backfilled with legacy provenance; capability and unit remain unknown for these historical records. Finalized reservations reject mutation; usage records reject mutation and truncation. The migration deliberately disallows automatic downgrade to protect recorded usage. This is reported quota usage, not a billing ledger: provider evidence, pricing, corrections, reconciliation, authorization, and production rollout remain outstanding.

Disposable PostgreSQL tests verify legacy backfill, old-writer capture, rollback, and mutation rejection. Production-scale migration behavior remains unverified.
## Tenant quota reads

The authenticated `GET /cloud/api/v1/tenants/{tenantId}/quotas` endpoint returns paginated persisted bucket limits, consumed amounts and outstanding reservations. Only the tenant's owner, administrator or billing reader may read them; membership includes both identity issuer and subject. The persistence query repeats the membership predicate when loading rows. Responses are not cached. Bucket amounts are operational quota counters, not invoices, finalized charges or a complete usage report. Offset pagination can shift if buckets are inserted or removed between requests. Quota policy administration, usage reporting and gateway enforcement remain outstanding.

The organization quota page uses the same authorized query service and displays periods in UTC. It clears previous organization data before loading another organization and ignores stale asynchronous results. The workspace links to it only for the permitted roles; the service remains the authorization boundary.

## Cloud privacy observations

Tenant owners, administrators and security analysts can read Cloud classification privacy observations through `/cloud/api/v1/tenants/{tenantId}/security/observations` and the organization security page. Issuer-bound membership is checked in the data query; successful and denied reads are recorded in the audit table before results are returned. The API supports UTC time bounds and a timestamp/ID keyset cursor, and the page offers UTC date filters. Observations are metadata-only Cloud decisions, not signed receipts, proof of application-host inspection, unique request counts, or proof of worker execution. The page states these limitations and does not display content. The added index uses a regular PostgreSQL migration; production-scale lock duration has not been measured. PostgreSQL, local authenticated HTTP and component tests cover role and tenant isolation, same-timestamp pagination, UTC bounds and audit behavior. Real-browser and deployed identity-provider checks remain outstanding.

An in-process Kestrel test with signed authentication cookies and disposable PostgreSQL exercises the quota HTTP route, including anonymous rejection, permitted billing access, cross-tenant and developer denial, paging, and page-size validation. This test uses a test-only cookie issuance endpoint; it does not verify a real identity-provider callback or deployed network.

## Cloud deployment inventory

Cloud deployments are stored separately from the process-local worker-kind registry. Each inventory record represents one capability, transport, region, contract version, opaque endpoint reference, concurrency limit, image digest and optional complete model identity/revision/digest. The internal registry validates the shape of these fields and uses optimistic revisions. It does not resolve endpoint references, verify signatures or artifacts, collect health, enforce concurrency, or authorize routing; configured records and digest strings are not evidence of readiness or integrity. PostgreSQL migration, multiple entries and revision conflicts were exercised against a disposable database. Authenticated health, artifact verification, residency policy, and gateway integration remain required before dispatch.

The authenticated operator inventory read API requires an enabled Cloud identity provider and an exact issuer and subject pair under `OpenConnect:Cloud:Operators:{index}:Issuer` and `OpenConnect:Cloud:Operators:{index}:Subject`. No entries means no operator access. The paginated API requires a capability filter and sends `Cache-Control: no-store`. A tenant role or application credential does not confer operator privileges. The configuration is deployment-controlled and changes require a configuration refresh; the API does not grant or manage operator access. The local HTTP tests use test-issued signed cookies, not an external identity provider.

Internal inventory writes require an actor and trace identifier. Successful writes and sanitized audit events commit atomically; validation failures, optimistic conflicts and database update failures attempt to write a separate audit event. Audit persistence failure prevents a successful response, but an unavailable database can prevent recording the failed attempt. The operator PUT endpoint requires the configured operator identity, an antiforgery token and a quoted `If-Match` revision (zero creates); it reads at most 8192 bytes of unencoded JSON only after those checks. It records authenticated authorization denials and validation failures without payloads and propagates the active W3C trace ID. Requests rejected by authentication middleware and disconnected clients are not guaranteed an audit event. Disposable PostgreSQL and local signed-cookie HTTP tests cover authorization, CSRF rejection, revision conflicts, bounded requests and audit outcomes; a real provider and deployed environment remain unverified.

The authenticated operator workspace lists deployments by catalog service, registers disabled entries and enables or disables existing entries using their current revision. The operator service rechecks the configured issuer and subject on each operation and uses the audited registry. Configured state is displayed separately from health and integrity, which remain unverified. A component test uses disposable PostgreSQL for registration, state changes and audit; real-browser and provider verification remain outstanding.

Membership role changes and removals record denied or conflicting store-level attempts in append-only audit records. A caller without tenant membership is recorded without a tenant association; a member denial identifies the tenant and a fingerprint of the target.
